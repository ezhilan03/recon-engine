# Synthetic Reconciliation Dataset

Generated by `src/recon_engine/data_gen/generate_dataset.py` (seed=42, 500 base transactions).

> Schema is grounded in a real external network settlement report format.
> See `docs/settlement_file_field_mapping.md` for the field-by-field mapping
> and which report sections this project models vs. omits.

## The core problem

`internal_ledger.csv` and `network_settlement.csv` share **no transaction-level
identifier**. This mirrors a real settlement-reconciliation problem: an external
settlement feed and an internal ledger that must be reconciled using only
circumstantial fields (date, amount, last-4, descriptor) — not a join key.
The only literally shared column is `account_last4`, which narrows candidates
but is not unique (multiple transactions per account per month).

## Files

- **internal_ledger.csv** — Spire's internal transaction record.
  `internal_txn_id, transaction_date, amount, account_last4, merchant_descriptor, nacha_return_code`
- **network_settlement.csv** — the external settlement feed. No internal ID.
  `settlement_line_id, settlement_date, gross_amount, fee_amount, net_amount, account_last4, descriptor, batch_id, return_code`
- **ground_truth.csv** — NOT an input to the matcher. Used only to score
  matching/resolution accuracy after the fact, the same role RAGAS ground
  truth played in Project 1.
  `internal_txn_id, settlement_line_ids (pipe-delimited), discrepancy_type, expected_cardinality`

## Discrepancy types seeded (10)

| Type | Cardinality | Matching challenge |
|---|---|---|
| clean_match | 1:1 | 1-2 day settlement lag |
| fee_variance | 1:1 | net_amount doesn't match a flat fee assumption |
| split_settlement | 1:many | one txn settles as two partial lines |
| batched_settlement | many:1 | multiple txns aggregate to one line; **account_last4 is not usable here** — only amount-sum + date-window |
| timing_outlier | 1:1 | settles 10-20 days late, breaks naive date-window joins |
| duplicate_line | 1:many (1 valid) | same txn appears twice in the settlement file |
| orphan_settlement | unmatched | settlement line with no internal record |
| orphan_internal | unmatched | internal txn that never settles |
| hard_return | 1:1, reversed | NACHA return code applied (real codes: R01-R29 subset), net_amount = 0 |
| descriptor_mangled | 1:1 | only the descriptor text is corrupted; other fields intact |

## Known modeling limitation

Batch settlement lines can only carry one `account_last4` (borrowed from
the first transaction in the batch) even though the underlying transactions
belong to different accounts. This is realistic for merchant-level batch
settlement, but it means a matcher that leans on `account_last4` for batches
will fail — intentionally, since that's the real-world constraint.
